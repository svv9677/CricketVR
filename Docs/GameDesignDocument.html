1. Overview & high concept

CricketVR is a single-player, first-person VR batting simulator. You stand at the striker's end of a full-size stadium, a motion-captured AI bowler runs in and delivers a physically-simulated ball, and you swing a tracked bat held in your dominant hand. Nine AI fielders and a keeper chase what you hit. A scoreboard tracks a short, compressed limited-overs match.

Platform & technical frame

  • Engine: Unity 2022.3.4f1 (ProjectSettings/ProjectVersion.txt). Upgraded from an older version in the most recent commit e8e5bec; the last commit that changed gameplay is 800c3c5, 2024-01-30.
  • Target: Android, AndroidMinSdkVersion 24, identifier com.RaoVadapalli.CricketVR, landscape-left default orientation (ProjectSettings/ProjectSettings.asset).
  • XR: Oculus XR loader (Assets/XR/Loaders/Oculus Loader.asset) with Android stereo rendering mode 2 (multiview) and V2 signing (Assets/XR/Settings/Oculus Settings.asset). A Windows MR loader is also present but unused. Rig is the Oculus Integration OVRPlayerController; the settings UI is the Oculus sample DebugUIBuilder.
  • Quality: current quality level index 2 ("Medium": 1 pixel light, hard shadows, no MSAA, no vsync) (ProjectSettings/QualitySettings.asset).
  • Physics tick: fixed timestep 0.007 s (~143 Hz) — deliberately high for a fast small ball (ProjectSettings/TimeManager.asset).

Target player & session fantasy

Built by the owner and his son as a personal project. The fantasy is being the batsman: read the bowler's type off the scoreboard, watch the ball out of a real run-up, swing, and watch it fly with a distance readout and an instant replay. The match model is deliberately compressed — 5 overs by default and no second innings — so a full "match" is roughly 30 deliveries. The owner describes it as cricket "slightly adapted for a faster turnaround of a match"; the adaptations that actually exist in code are listed in §2.

Inferred No menu, tutorial, onboarding or end-of-match screen exists. The game state machine's None state comments // For now, skip the menus and jumps straight into play (Main.cs:946–950). The "session" as shipped is: put the headset on, you are already at the crease.

2.3 Runs from a struck ball — the "running" abstraction

This is the single biggest adaptation of real cricket. There is no running between the wickets and no run-out. Instead, runs are awarded from the wall-clock time between bat contact and the ball being fielded: the longer the ball is loose, the more you score.

2.5 Extras

  • Wides are implemented. Two box triggers sit on the batsman's stump line at x = 10.3, size 1 × 15 × 6, and slide laterally to follow the player each frame (WideCollider.cs:19–43). If the player stands central, the legal corridor is roughly z ∈ (−0.3, +1.2), i.e. about 1.5 m wide, and it is deliberately asymmetric — the off-side collider sits further out (offset 1.08/1.2) than the leg-side one (offset 0.18/0.3).
  • A wide adds 1 run and does not count as a ball, exactly as in real cricket (HUD.cs:265–270). The over-separator logic in the scoreboard string skips wd when counting to six (HUD.cs:391–399).
  • Byes and leg-byes are not implemented. The code says so explicitly: // Ball was missed: possible outcomes - dot ball, wide(s) or bye(s) / For now, not using extras in the game (HUD.cs:177–178).
  • No-balls are not implemented. There is no front-foot line, no beamer/bouncer height check. The only surviving trace is a commented-out clamp in BowlingProfileManager.cs:203–208 that once limited spin speed "to not throw a no-ball".

Code bug A wide credits the run to the striker's personal score, not to extras: case 10 calls IncrementRuns(1), which does CurrentBatsman.Runs += runs (HUD.cs:267, HUD.cs:331–335). Real cricket books this as an extra.

2.6 How an over, an innings and the match end

  • End of over (HUD.cs:337–357): on the 6th legal ball, Balls resets to 0, Overs++, the batsmen swap ends, and SelectNextBowler() advances to the next bowler in the list, wrapping round after the 8th (HUD.cs:281–292). The new bowler's type is pushed into Main.swingType, the keeper is repositioned, and the bowler model's run-up config is swapped.
  • End of innings: not implemented. When Overs == TotalOvers the code only writes Debug.LogWarning("MATCH DONE!!!!") and play continues into a 6th over (HUD.cs:352–355).
  • All out: not implemented. When the next-batsman index passes 10 it logs "GAME OVER!! ALL OUT" and then wraps the index back to 0, so the same batsmen simply come round again (HUD.cs:370–375).

Gap The match cannot end. Both terminal conditions are console log lines. Nothing resets the scoreboard, shows a result, or returns to a menu. This is the single largest missing piece of the ruleset and matches the owner's pending items "UI for final results" and "UI for initial menu".

NOTES vs code NOTES marks Scoring Mechanism as ~ (in progress). In reality the per-ball scoring model in HUD.cs is essentially complete — runs, wickets, overs, strike rotation, bowler rotation, run rate, and a ball-by-ball scorecard string all work. What is missing is (a) terminating the innings/match, (b) any fanfare or result UI, and (c) extras beyond wides. Treat "scoring" as done at the ball level, absent at the match level.

3. Core gameplay loop — ball by ball

The loop is an explicit state machine in Main.Update() (Main.cs:944–1137). Each "real" state does its work once and immediately falls through to a matching ...Loop state, which waits for an external trigger — a collider, a coroutine, or an animation event. The whole switch is skipped while the settings menu is open (Main.cs:942).

Player-facing rhythm: green light → press A → bowler runs in (~3–5 s of animation) → ball → swing or miss → 2–4 s of outcome and replay → 2 s reset → green light again. Roughly 10–15 s per ball, so a 5-over match is about 6–8 minutes of play.

Inferred Pressing X at any moment force-jumps to InGame_ResetToReady (Main.cs:936–939), under the comment // Temporary stuff. It is an escape hatch for stuck balls, not a designed feature — and because the state machine skips the scoring states, a ball abandoned this way is never scored.

4. Player mechanics — VR batting

4.1 Holding the bat

The bat is never physically grabbed. It is hard-parented to the dominant hand anchor every LateUpdate, with a per-hand position and rotation offset (Bat.cs:307–339):

  • battingStyle (Right/Left) selects rightHandParent or leftHandParent as attachParent (Main.cs:519–548). Default is right-handed (Main.cs:259, PlayerPrefs key style).
  • Only the right-hand grab offsets are overridden in the scene; the left-hand offsets sit at the prefab defaults.
  • SetBatIgnoreHandCollision(true) disables physical collision between bat and hand colliders while held (Bat.cs:91–103).
  • The bat is hidden entirely while the settings menu is open (Main.cs:1165, 1172).

4.2 The bat collider

In the scene the bat carries a trigger BoxCollider of size (0.25, 0.25, 1.2) on a kinematic rigidbody. Difficulty scales only the x (width) axis:

4.3 The custom bat–ball collision (the "momentum" model)

The git log records the key change: "Changed bat and ball collision from collider to trigger and calculated it manually." The handler is Bat.OnTriggerEnter (Bat.cs:106–268) and runs once per delivery, guarded by hasHitBall.

  1. Capture incoming velocity. ballInitialVelocity = theBallScript.lastVelocity — the ball's velocity as of the previous LateUpdate (Ball.cs:144–147). This is deliberately the post-bounce velocity, per the comment at Main.cs:1022.
  2. Reflect off the bat face. The bat's local up is the blade normal. Let angle = 180° − Angle(bat.up, ballInitialVelocity). If angle < 45°, the ball is reflected ((−v).normalized + bat.up); otherwise it is deflected forward (v.normalized + bat.up), in both cases renormalised and rescaled to the incoming speed (Bat.cs:196–206). dampenFactor is hard-coded to 1, i.e. no energy loss.
  3. Add the swing. avgBatSpeed is the mean of the last 5 frames of tracker-position delta magnitude (Bat.cs:208, Bat.cs:292–305). batSwing = bat.up × cos(Angle(bat.up, trackerVelocity)) × avgBatSpeed — i.e. only the component of hand motion along the blade normal contributes (Bat.cs:211).
  4. Combine. finalVel = (ballBounce / 75 + batSwing) × BatAmplifier × contactRadius, with BatAmplifier defaulting to 75 (slider 50–200) and contactRadius hard-coded to 1. With the default amplifier this reduces to ballBounce + 75 × batSwing — the deflected ball speed plus a heavily amplified swing term (Bat.cs:212–215).
  5. Feedback. Controller vibration at full amplitude for 0.1 s on the batting hand (Bat.cs:276–289), one of three impact sounds (§9), a distance readout, and — if the debug overlay is on — four coloured world-space arrows showing ballBounce, batSwing, bat.up and tracker velocity (Bat.cs:243–255).
  6. Replay camera switches to the chase view after 1 s (Bat.cs:258).

Gap Sweet spot is not modelled. contactRadius = 1f; // TODO insert calculation for distance to contact (Bat.cs:192) and float dampenFactor = 1f; with a matching TODO in the commented-out older path (Bat.cs:163–164). Every contact anywhere on the blade produces identical power. This is the most obvious lever for "feel" work.

Dead code Bat.cs:191–193 computes batMomentum from myRigidBody.velocity + myRigidBody.angularVelocity * contactRadius. The bat's rigidbody is kinematic and moved by transform, so both are always zero — and the variable is never read afterwards. The real "momentum" comes from trackerVelocity, not from physics.

Inferred / unit bug trackerVelocity is a raw per-frame position delta (Bat.cs:294) — metres per frame, not metres per second — yet BallSpeed.updateBatAndFinalSpeed converts it as if it were m/s (BallSpeed.cs:39). The displayed "Bat: N kph" is therefore off by a factor of the frame rate. The gameplay is unaffected because BatAmplifier was tuned against the same wrong-unit quantity, but any frame-rate change silently changes shot power.

Other per-delivery parameters:

  • torqueX = director × 50, where director is −1 for InSwing/OutSwing and 11 for everything else → −50 for swing bowlers, +550 for pace and spin (BowlingProfileManager.cs:191, 194). Applied as an impulse torque about world X (Main.cs:1006, 1017), with maxAngularVelocity raised to 100 (Ball.cs:30). This is the visible seam rotation.
  • applySwing = Random(0,1) > 0.05 || type is In/Out swing → in-air swing on ~95% of deliveries, always for swing bowlers (BowlingProfileManager.cs:200).
  • applyPitchTurn = Random(0,1) > 0.15 || type is Leg/Off spin → turn off the pitch on ~85% of deliveries, always for spinners (BowlingProfileManager.cs:201).
  • Line/swing coupling: when an in-swinger rolls a large swing value, its starting line is clamped to the off-side half of the range; the mirror clamp applies to out-swingers (BowlingProfileManager.cs:210–220). This keeps a big swinger from starting on the stumps and finishing a metre outside them.

5.3 Release and trajectory solve

On InGame_DeliverBall the ball is unparented from the bowler's hand, made dynamic with continuous-dynamic collision and interpolation, then given a torque impulse and a force impulse (Main.cs:1001–1031). The vertical component is solved rather than randomised:

GetYVel(startPos × 3.28, speedX / mass × 3.28, length × 3.28) (Main.cs:1008, implementation Main.cs:1291–1301) works in feet: time = (length − startPos.x) / startVelX, then startVelY = 16 × time + (height − startPos.y / time) with height = 0.1. The result is converted back to a metric impulse at Main.cs:1009.

Suspect The expression (height - startPos.y / time) almost certainly should be ((height - startPos.y) / time) — as written, only startPos.y is divided by time. Two earlier, physically-correct projectile solves sit commented out immediately above and below it (Main.cs:1149–1156, 1280–1287, 1345–1352). The current version is empirically tuned, not derived; this is worth revisiting before retuning lengths.

5.4 Swing in the air, turn off the pitch

  • In-air swing (Ball.cs:99–124, only during DeliverBallLoop): a drag-like magnitude F = (ρ v² Cd A)/2 with tuned constants ρ = 0.25, Cd = 0.25, A = π × 0.0575², then multiplied by 10 and by the delivery's swing value. The direction is Cross(±flightDir, up) with x and y forced to zero — so the force is purely lateral along world Z. InSwing and LegSpin go one way, OutSwing and OffSpin the other; Random picks a side 50/50.
  • Actual air resistance is disabled. The backward drag AddForce is commented out at Ball.cs:96–97 with the note that the formula is now used only to size the swing force.
  • Turn off the pitch (Ball.cs:160–197): on the first contact with a Ground-tagged collider, fresh goes false, applySwing is switched off, and a lateral impulse right × pitchTurn × |v| × 0.1 is applied — direction reversed relative to the in-air swing, so a ball that swings in then turns away, as a real leg-break does. Per the comment at Ball.cs:174, in-swing is treated as leg-spin and out-swing as off-spin for this purpose.

5.5 Randomisation points

The NOTES pending item "Identify all randomization points" — here they are, all of them:

  1. speedX, length, speedZ, swing, pitchTurn: uniform in the profile range (BowlingProfileManager.cs:195–199).
  2. applySwing 5% off-chance, applyPitchTurn 15% off-chance (BowlingProfileManager.cs:200–201).
  3. Swing/turn side for eSwingType.Random only: 50/50 (Ball.cs:105, Ball.cs:181).
  4. Profile choice when the type is Random: uniform over the five profiles (BowlingProfileManager.cs:250–263). Not reachable in normal play — swingType always comes from the named bowler.
  5. Ball velocity damping on stump contact: random 2–5 m/s (Stump.cs:46).

6. Fielding & AI

6.1 Who is on the field

  • Nine animated fielders, AFielder_01 … AFielder_09, each running AnimatedFielder.cs. Their home positions come from Constants.fieldingPositions (Constants.cs:79–88), indexed by the last digit of the GameObject name (AnimatedFielder.cs:73). The spread ranges from ~21 m (short cover at (10, 0, 19)) out to ~54 m (deep at (−54, 0, −5)).
  • One keeper, Fielder_Keeper, an instance of Fielder.prefab running the older Fielder.cs. isKeeper is set at runtime by name match (Fielder.cs:40–41). He does not chase; he is repositioned per bowler type (§5.1).
  • A disabled legacy set: an Old Fielders group holding Fielder_01…Fielder_09 (iTween-driven Fielder.cs) sits in the scene with m_IsActive: 0. It is the pre-animation implementation, kept for reference.
  • One field setting only. There is no per-bowler field, no captaincy, no attacking/defensive field.

6.2 Fielder behaviour by phase

  • Between balls — fielders snap back to their home position and look at the middle; all chase flags reset (AnimatedFielder.cs:174–212).
  • During the delivery — every non-keeper walks 2 m forward (the "taking start" creep) via an iTween move at Main.fielderSpeed (default 1.5, slider 0.5–2.5) (AnimatedFielder.cs:214–230).
  • On a shot — each fielder solves an intercept, then only the three fastest actually chase (see below).
  • Interception — AnimatedFielder.Update() looks ahead by |v| × Δt × 30 and claims the ball when it is inside pickUpDistance and the projected ball position is within (1/22) × 30 ≈ 1.36 m, but only if no other fielder has claimed it (AnimatedFielder.cs:139–163). A simple within-1 m check also claims it.
  • Pick-up — plays animator state 4 Pick Up; at 29% through the clip the ball snaps to a hand bone, then goes kinematic and the state becomes InGame_BallFielded (AnimatedFielder.cs:605–658).

6.3 The intercept solver

GetInterceptPoint() (AnimatedFielder.cs:663–738) is a closed-form pursuit solution: given the fielder's position (a, c), the ball's position (b, d) and ground velocity (e, f), and a runner speed g, it solves for the run angle whose straight-line chase meets the ball, takes the smallest positive time, and returns (interceptX, interceptZ, time). Both roots are wrapped in try/catch into an intentionally empty handler (AnimatedFielder.cs:797–800); if no real root exists the fielder instead targets where the ball would cross the boundary and marks isBallReachable = false (AnimatedFielder.cs:693–700).

  • Runner speed is g = 2.9 / 22 / Time.deltaTime (AnimatedFielder.cs:672) — 2.9 m of root motion over 22 animation frames, converted to per-second. At 72 fps that is about 9.5 m/s, which is sprinter-fast. Note this means fielder speed is frame-rate dependent, and that the fielderSpeed slider does not affect it — the slider only drives the iTween "taking start" creep and the legacy Fielder.cs.
  • Arbitration: AnimatedFielderManagement.LateUpdate() waits until all 9 intercept times are in, sorts them, and sets shouldFieldBall = true for exactly the three fastest (AnimatedFielderManagement.cs:32–47). Ties are broken by nudging duplicate keys down by 0.01 (AnimatedFielder.cs:294–301).
  • There is a second, unused solver GetInterceptPoint2() (AnimatedFielder.cs:740–795) that additionally takes a reaction delay d.

6.4 Catches, boundaries and throws

  • Catches are not animated. The 6 Catch animator state exists in Fielder Controller.controller and Catch.anim is authored, but the code only ever plays 4 Pick Up. The explicit TODO reads "Insert logic for choosing between the 'Catch' animation and the 'Pick Up' animation based on the height of the ball" (AnimatedFielder.cs:620–622). A catch is therefore just "picked up before it bounced".
  • Throws are not implemented. "Insert logic for throwing: calculating distance, speed and angle of throw" (AnimatedFielder.cs:641–643). The fielder simply holds the ball until the reset.
  • Boundary: a CapsuleCollider trigger, radius 56 × local scale 1.3333 ≈ 74.7 m, height 200 (≈266 m tall), so effectively a vertical cylinder around the ground. OnTriggerExit fires only while in InGame_BallHitLoop (BoundaryCollider.cs:5–14). The same radius is read back by the fielder AI when no intercept exists (AnimatedFielder.cs:696).
  • Keeper plane: a 1 × 15 × 25 box trigger parented to the keeper. When the ball exits it during DeliverBallLoop, the delivery is a miss (KeeperCollider.cs:7–26). The same script is also attached to both wide colliders, where it additionally sets wide = true by checking gameObject.name.Contains("WideCollider").

NOTES vs code NOTES marks AI Fielders as done (√). The chase, arbitration and pick-up are indeed working — but with no catch animation, no throw, no dive, no misfield and no run-out, the fielding side is a scoring oracle rather than an opponent. Treat "AI Fielders" as movement done, fielding actions not started.

Inferred The pitch's bounciness of 0.7 against a ball bounciness of 0.35 combined with maximum (bounceCombine: 3) means the effective restitution off the pitch is 0.7 — a very lively surface. Combined with the swing force being multiplied by an arbitrary 10× and the bat's 75× amplifier, the physics is best described as tuned by feel against a set of magic numbers, not derived. Any retune should change one at a time.

8. UI / UX & HUD

8.1 The scoreboard (HUD.prefab, world-space, in front of the player)

Driven by HUD.UpdateUI() (HUD.cs:378–419). It shows:

  • Runs/Wickets, e.g. 37/2
  • Run rate (raw float, unformatted)
  • Both batsmen's names and individual scores; striker first
  • Overs as O.B (total), e.g. 3.4 (5)
  • Current bowler's name and style label from Constants.CT_SwingPrefixes — none, pace, inSwing, outSwing, legSpin, offSpin, random (Constants.cs:39)
  • A reversed ball-by-ball string (W, *, 1–6, wd) with | separators every six legal balls

HUD depth is adjustable 3–5 m via a slider, persisted as hud_offset (Main.cs:656–681).

Code smell The txtVersion label is hijacked as an FPS counter — theHUD.txtVersion.text = (1f / Time.deltaTime).ToString(), every frame, unrounded (Main.cs:1146). The real version line is commented out at HUD.cs:380 because PlayerSettings is editor-only. HUD.cs also still has a top-level using UnityEditor; (HUD.cs:3) — this will fail an Android player build unless it is removed or wrapped in #if UNITY_EDITOR.

8.2 In-world displays (scene group Displays)

  • Ball Speed (BallSpeed.cs): three fixed-updates after release it prints Release: N kph; after bat contact it appends Bat: N kph and Bounce: N kph (the outgoing shot speed). See the unit caveat in §4.3.
  • Shot Distance (ShotDistance.cs): live 2D (ground-plane) distance between ball and bat, rounded to 0.1 m, updated every FixedUpdate while the ball is live, reset to 0.0 m on each new delivery. The predictive landing-point version of this (calculateDistance) is entirely commented out (ShotDistance.cs:44–64) and is called but does nothing (Bat.cs:241).
  • Test Display (TestDisplay.cs): impact diagnostics — four coloured arrows instantiated from Arrow.prefab (red = ball bounce vector, yellow = bat swing, green = bat face normal, blue = tracker velocity) plus the raw numbers. Only shown when the overlay is on (Bat.cs:243–255).

8.4 Replay camera

CameraReplay.cs captures the replay camera's render texture into a List<Texture2D> every 7 fixed updates and plays it back onto a material at 1× speed, looping with a 1 s pause (CameraReplay.cs:73–143). Two framings:

  • View 0 — fixed position, field of view 7° (a long lens on the pitch).
  • View 1 — repositions to (−14, 1.78, 0) and tracks the ball with a 60° FOV; engaged 1 s after bat contact (Bat.cs:258).

Recording starts at release, and stops with a type-dependent tail: 2 s after a shot, 1 s after being bowled, immediately on a miss (Main.cs:1047, 1078, 1094).

Performance risk / unverified Every replay frame is a full new Texture2D allocation held in a list until the next delivery (CameraReplay.cs:98–100). At 143 Hz fixed step and one capture per 7 steps that is ~20 textures per second of play. On Quest hardware this is the most likely source of hitching or memory pressure; it has not been profiled here.

12.1 Where NOTES and the code disagree — summary

  1. Scoring is further along than NOTES claims. Marked ~, but per-ball scoring, strike rotation, bowler rotation, run rate and the ball-by-ball scorecard all work. The real hole is match termination and result UI.
  2. AI Fielders is less complete than NOTES claims. Marked √, but catching and throwing — the two actions that make fielding a threat — are unwritten TODOs.
  3. "Bat physics ... (ongoing)" is accurate, and the ongoing part is specifically sweet-spot/contact-point modelling.
  4. The dead legacy layer is larger than NOTES suggests. AnimatedFielderUnchanged.cs (803 lines) differs from AnimatedFielder.cs by exactly one commented-out line and is attached to nothing; the entire Old Fielders group is disabled; Assets/Editor/CustomEditorScript.cs is 100% commented out; BowlingProfileManager.cs carries a full commented-out earlier copy of its own classes.

13. Known gaps & design questions for the revival

13.1 Must-decide design questions

  1. What ends a match? Today nothing does. Options: 5 overs, all-out at 10 wickets (currently the batting list wraps instead), or a target-chase mode. Whatever is chosen also needs a reset path — HUD.Reset(totalOvers) already exists and takes a parameter that nothing supplies.
  2. Is 5 overs right? It is a default argument, never surfaced to the player. Should overs be a menu choice (3 / 5 / 10)?
  3. Keep the time-based running model, or build real running? The elapsed-seconds table (§2.3) is the boldest adaptation in the game and is what makes a match fast. Building real running-between-wickets would unlock run-outs and a reason for fielders to throw — but would slow the loop and needs a locomotion answer in VR.
  4. What should difficulty actually change? The bat collider alone is a blunt instrument. Candidates, all already parameterised: speed ranges, swing/pitchTurn ranges, length spread, wide corridor width, fielder count in the chase (currently fixed at 3), and a catch-drop probability once catching exists.
  5. Should the bowling machine come back, or go? It is now only a green/red ready light while an animated bowler does the work. Either delete it and replace the ready signal with something diegetic, or restore the "slide and pick a spot" plan as a visible telegraph of line.
  6. Who is the second team? There is no opponent score, no toss, no result. A one-innings high-score run may be the honest framing for this game — that is a design decision, not an omission to fix by default.
  7. Is the boundary the right size? ~74.7 m radius from the ground origin is generous; combined with the 75× bat amplifier it may make sixes either trivial or impossible. Worth measuring before retuning the bat.

13.2 Technical debt to clear before feature work

  • Verify the project still builds and runs on current Quest firmware after the 2022.3.4f1 upgrade. The upgrade commit changed nothing else, so it has almost certainly never been run on-device.
  • Remove using UnityEditor; from HUD.cs:3 (and the commented PlayerSettings.bundleVersion line at HUD.cs:380) or guard them — this is a build-breaker for Android players.
  • Stop hijacking txtVersion as an FPS counter (Main.cs:1146) — and if an FPS readout is wanted, round it.
  • Make shot power frame-rate independent. trackerVelocity should be divided by Time.deltaTime and BatAmplifier retuned once, rather than leaving power coupled to headset frame rate (Bat.cs:294).
  • Make fielder speed frame-rate independent for the same reason (AnimatedFielder.cs:672), and either wire the fielderSpeed slider to the animated fielders or relabel it.
  • Fix or intentionally keep the GetYVel parenthesisation (Main.cs:1296) — see §5.3. Lengths cannot be trusted until this is settled.
  • Replace the stump-motion heuristic with an actual ball-to-stump contact test, so that the batsman brushing the stumps is scored as hit-wicket (or not at all) rather than as bowled (Stump.cs:19–26).
  • Delete the dead layer: AnimatedFielderUnchanged.cs, the disabled Old Fielders group, Assets/Editor/CustomEditorScript.cs, the commented class copies in BowlingProfileManager.cs, the commented bat path in Bat.cs:121–187, and the PARTICLE-tagged particle code in Ball.cs. ~2,000 lines of noise that will otherwise mislead whoever picks this up.
  • Book wides as extras rather than crediting the striker (HUD.cs:267).
  • Profile the replay texture allocation (CameraReplay.cs:98) on-device before adding any more per-frame work.
